# Frontend/Backend Gap Report — Phase 0

Nine gaps found comparing the TezRecovery design against the actual `admill-backend` implementation. None are blocking for Phase 1 (RN project setup) or Phase 2 (design system) — they matter starting Phase 4/6 (Customer/Driver/Owner screens) when the specific flows below are built.

---

### 1. OTP / phone verification login
- **Frontend design expects**: a dedicated OTP entry screen as part of the auth flow.
- **Backend currently provides**: email + password only (`POST /auth/login`, `POST /auth/register`). No SMS provider, no OTP generation/verification endpoint anywhere in the codebase.
- **Missing backend capability**: OTP send + verify endpoints, SMS provider integration.
- **Frontend impact**: the OTP screen has nothing to call. Cannot be implemented as designed without backend work.
- **Recommendation**: build the auth flow against email+password for now (skip/hide the OTP screen), and treat OTP as a future backend milestone if still wanted.

### 2. In-app chat (customer ↔ driver)
- **Frontend design expects**: a chat screen for customer/driver messaging on an active job.
- **Backend currently provides**: nothing — no message model, no REST endpoints, no socket events for chat.
- **Missing backend capability**: a messaging feature end-to-end (persistence + real-time delivery).
- **Frontend impact**: chat screen has no data layer to build against.
- **Recommendation**: omit for now, or scope a real backend messaging milestone before building this screen. Do not fake it with a client-only/local-only chat.

### 3. Customer "vehicles" on profile
- **Frontend design expects**: a vehicles section under the customer's profile.
- **Backend currently provides**: `Vehicle` is a company fleet asset (owned by a company, optionally assigned to a driver) — there is no concept of a customer owning/registering a vehicle.
- **Missing backend capability**: a customer-owned vehicle model (if that's actually the intent — e.g. "the car that needs recovering," saved for faster future bookings).
- **Frontend impact**: this section can't be wired to anything real today.
- **Recommendation**: needs a product decision first — is this meant to be "vehicles I've requested recovery for" (a new, small backend feature) or a design artifact from a different product concept that should be dropped? Flagging rather than guessing.

### 4. Sequential "matching" animation
- **Frontend design expects** (as understood from the interactive prototype): a matching flow that appears to search/step through drivers.
- **Backend currently provides**: a single broadcast — all eligible nearby drivers are offered the job simultaneously at creation (`offeredDriverIds` snapshot), first to accept wins.
- **Missing backend capability**: none needed — this is a design-vs-model mismatch, not a missing feature.
- **Frontend impact**: a literal "asking driver 1... driver 2... driver 3" animation would be fabricating information the backend doesn't have (the server doesn't ask sequentially).
- **Recommendation**: build the matching screen as a single indeterminate "finding your driver" state that resolves on `job:accepted`, not a sequential per-driver animation.

### 5. Receipts / invoice generation
- **Frontend design expects**: a receipt view/download in job history.
- **Backend currently provides**: raw job fields only (`finalFare`, locations, timestamps) via `GET /jobs/:id`. No formatted receipt/invoice/PDF generation endpoint.
- **Missing backend capability**: receipt generation (and likely a template, given `CompanySettings.invoiceBranding` already exists as a field — suggesting this was planned but not built).
- **Frontend impact**: can show a basic in-app summary from existing job fields; cannot offer a downloadable/shareable formatted receipt.
- **Recommendation**: build a simple in-app summary screen from existing fields now; treat PDF/formatted receipts as a follow-up backend feature (there's already a hook for it in `CompanySettings.invoiceBranding`).

### 6. Route polyline / turn-by-turn navigation — route LINE resolved 2026-08-13 (Phase 5); turn-by-turn navigation still not attempted (never in scope)
- **Frontend design expects**: a visible route line and/or turn-by-turn navigation during an active job.
- **Backend currently provides**: `distanceKm`/`durationMinutes` only (from the pricing engine) — no route geometry/polyline. Unchanged by the resolution below — still not an Admill backend concern.
- **Missing backend capability**: none needed — this is inherently a client-side maps-SDK concern (Google/Mapbox directions), not something the Admill backend should provide.
- **Frontend impact**: none, provided the RN app calls a maps/directions provider directly for the route line, using pickup/destination coordinates it already has.
- **Recommendation**: use `react-native-maps` + whatever directions API the chosen map provider offers, independent of admill-backend.
- **Resolution — route line only (Phase 5, 2026-08-13)**: `src/utils/directions.ts`'s `getRoute()` calls Google's **Routes API** (`routes.googleapis.com`, the modern replacement for the legacy Directions API — Google's own error response steered toward it when the legacy one was tested against this project's key and found not enabled) using `job.pickupLocation`/`destinationLocation` (already available on every `Job`, at any status). Decodes the returned encoded polyline (Google's standard algorithm, hand-implemented, no new dependency) and renders it via `react-native-maps`'s already-installed `<Polyline>` on both `CustomerJobDetailScreen.tsx` and `DriverJobDetailScreen.tsx`. **Never throws** — no key configured, API not enabled/authorized, network failure, an 8s timeout, or no route found all resolve to `null`, and the screen falls back to the pre-existing markers-only map, exactly as it worked before this feature existed. **`GOOGLE_MAPS_API_KEY` is now also read from JS** (`src/config/env.ts`) — previously documented as native-only (Maps SDK meta-data). At the time of this change, this project's Google Cloud key had **Routes API not enabled** (confirmed via a live test call, response `REQUEST_DENIED`) and is restricted for native "Android apps" use (package+SHA-1), a restriction type that doesn't apply to a plain client-side REST call — a key with Routes API enabled and an appropriate quota cap is required before routes will actually render; until then this feature is fully built and tested but dormant (its fallback path is what's currently live). Turn-by-turn navigation (voice guidance, live re-routing) was never attempted and remains genuinely out of scope.

### 7. Driver earnings breakdown (by day/week/period)
- **Frontend design expects**: an earnings screen, plausibly with period breakdowns.
- **Backend currently provides**: no driver-facing earnings endpoint at all (analytics is OWNER-only). A driver's own `GET /jobs?status=COMPLETED` (already scoped to their assigned jobs) can be summed client-side for a running total.
- **Missing backend capability**: a driver-facing earnings summary/period-bucketed endpoint.
- **Frontend impact**: a simple lifetime-or-visible-page total is buildable now by summing `finalFare` client-side; a proper day/week/period breakdown is not, without fetching and locally bucketing potentially many pages of jobs.
- **Recommendation**: ship a simple running total first; treat period-bucketed earnings as a small backend follow-up if the UX needs it.

### 8. Owner manual job assignment
- **Frontend design expects**: an owner picking/assigning a specific driver to a job.
- **Backend currently provides**: assignment only happens via the broadcast-and-first-to-accept flow; no owner endpoint to directly assign a job to a chosen driver.
- **Missing backend capability**: an owner "assign job to driver X" endpoint.
- **Frontend impact**: the owner "Job Management/Assignment" screen can show/monitor jobs and drivers, and cancel jobs, but cannot manually assign one.
- **Recommendation**: build the monitoring/cancel parts now; flag manual assignment as a backend follow-up if the owner workflow needs it (this is a real, useful gap, not a design mismatch).

### 9. Driver suspension / leave (owner-controlled)
- **Frontend design expects** (if present — a plausible owner fleet-management action): suspending or placing a driver on leave.
- **Backend currently provides**: `ON_LEAVE`/`SUSPENDED` exist in the `DriverStatus` enum, but no endpoint sets them (only `AVAILABLE`/`OFFLINE`/`ON_BREAK` are driver-self-settable; approve/reject are the only owner-driven status actions).
- **Missing backend capability**: an owner endpoint to set a driver's status to `ON_LEAVE`/`SUSPENDED` (and presumably reinstate).
- **Frontend impact**: cannot build a "suspend this driver" owner action as-is.
- **Recommendation**: small backend follow-up if the owner fleet-management screen needs this action; otherwise omit.

### 10. No `GET /drivers/me` — RESOLVED in Phase 3 (2026-08-10)
- **Original finding** (Phase 1, 2026-08-09): a driver could not look up their own profile without a locally-cached id — only `GET /drivers/:id` existed, unlike Company/Customer's `/me` shortcuts.
- **Resolution**: `GET /drivers/me` implemented in `admill-backend` (`src/modules/driver/{driver.routes,driver.controller,driver.service}.ts`), mirroring `CustomerService.getMyProfile` exactly — resolves the driver via `DriverRepository.findByUserId(req.user.id)` (never trusts client input), then returns the identity-populated profile via the existing `findByIdWithIdentity`. No new repository methods were needed — both already existed. `DRIVER`-role-gated, 404 `"Driver profile not found"` if the caller never completed `POST /drivers`. 5 new integration tests in `tests/integration/driverMe.test.ts` (own profile / no-profile 404 / wrong-role 403 / unauthenticated 401 / reflects live approval-status changes), full backend suite re-run to confirm no regressions.
- **Frontend impact**: the mobile app's `src/api/drivers.api.ts` (`getMyDriverProfile`) now calls `GET /drivers/me` directly. The Phase 1 local-id-cache workaround (`src/auth/localCache.ts`) is no longer needed for this lookup and is removed in Phase 3 — a driver on a new device now gets their own profile back immediately after login, no registration-flow dependency.
- **This was the only backend change made in Phase 3**, per the explicit change-control instructions for this phase — no other backend files were touched.

### 12. No driver-facing "my assigned vehicle" lookup (discovered during Phase 3 implementation, 2026-08-10)
- **Frontend design expects**: a Driver app screen showing the vehicle currently assigned to the logged-in driver (plate number, type, recovery services, documents).
- **Backend currently provides**: the assignment relationship is stored only on `Vehicle.assignedDriver` (verified — `IDriver` has no vehicle reference field at all), and `GET /vehicles` (the only way to search/list vehicles by `assignedDriver`) is `requireRole(OWNER)`-only. `GET /vehicles/:id` does allow "the driver currently assigned to it," but only if the driver already knows the vehicle's `_id` — there is no way to discover that id from the Driver side.
- **Missing backend capability**: either a `GET /vehicles/me` (mirroring the `GET /drivers/me` pattern just added), or an `assignedVehicleId` field surfaced on the Driver profile response.
- **Frontend impact**: implemented the closest truthful workaround — `useMyAssignedVehicle` (`src/features/driver/vehicle/`) looks at the driver's own recent jobs (`GET /jobs`, already self-scoped) for the most recent one with a `vehicleId` set, then fetches that vehicle via `GET /vehicles/:id` (which the driver is allowed to call once the id is known). This is real data, not fabricated, but it's best-effort: a driver who hasn't completed any job yet, or who was reassigned to a different vehicle without a new job since, may see no vehicle or a stale one. The Vehicle screen states this plainly rather than presenting it as an authoritative "your vehicle" record.
- **Recommendation**: a small backend addition (`GET /vehicles/me` for the DRIVER role, same pattern as gap #10's resolution) would fix this properly — flagged for consideration in a future phase, not implemented here per this phase's change-control scope (only `GET /drivers/me` was pre-authorized).

### 13. Customer cannot see their assigned driver's identity, photo, or rating (discovered during Phase 4 preflight, 2026-08-10) — RESOLVED 2026-08-13 (Phase 5)
- **Frontend design expects**: the Customer live-tracking screen (design step C-05) shows the assigned driver's name, avatar, star rating, and vehicle plate ("Ahmed Hassan · ★4.94 · 1,208 jobs · DXB-42718"), plus call/message affordances.
- **Backend currently provides**: nothing customer-reachable. Verified directly against source (`driver.service.ts`'s `assertDriverAccess`, `2026-08-10`): `GET /drivers/:id` and `GET /drivers/:id/ratings` only permit the driver themself or the owning company's OWNER — `CUSTOMER` is not in the allow-list at all and always gets 403, with no carve-out for "customer on an active job with this driver." A `Job` document only ever stores `driverId`/`vehicleId` as bare, unpopulated ids (confirmed in `types/entities.ts` and the backend's `job.repository.ts`), so there is no other route to a name/photo either.
- **Partial exception — location only**: `GET /drivers/:id/location` (`tracking.service.ts`'s `assertCanViewDriverLocation`) *does* have a customer carve-out, but it is narrower than "active job": it only checks `JobRepository.findActiveByDriverId`, which matches `status IN [EN_ROUTE, STARTED]` — **not** `ACCEPTED` (driver just assigned, hasn't started moving) or `ARRIVED` (driver on-site, job not yet started). And even when it succeeds, the response is `{driverId, location}` only — no identity fields.
- **Also confirmed dead**: `Customer.averageRating`/`Customer.totalJobs` exist as schema fields (`customer.interface.ts`) but are never written by any code path in the backend (grepped `src/modules/`, `src/repositories/` — zero writes). They will always read as their Mongoose default; do not build a Customer profile "stats" card that trusts these two fields as real data.
- **Missing backend capability**: either (a) a driver-identity-populated field on the `Job` response when the requester is that job's customer, or (b) a customer-scoped carve-out on `GET /drivers/:id`/`.../ratings` mirroring the one `.../location` already has (and widening that carve-out's status check to include `ACCEPTED`/`ARRIVED`).
- **Frontend impact**: the Customer "driver assigned"/live-tracking screen can show live GPS position only while `EN_ROUTE`/`STARTED` (map + ETA), a generic "Your driver" label, and the driver's phone number **cannot** be surfaced for a tap-to-call affordance (not returned by any customer-reachable endpoint) — must omit call/message-driver actions entirely rather than fabricate a contact method, and must not render a driver name/photo/rating anywhere in the Customer app. Chat (gap #2) was already omitted for lacking a backend entirely; this closes off even a *fallback* "at least show who they're texting" affordance.
- **Recommendation**: flagged for a future backend milestone — not implemented here, per Phase 4's preflight-only scope (no backend changes are in scope for this audit).
- **Resolution (Phase 5, 2026-08-13)**: took option (a) — `GET /jobs/:id`'s response now includes `assignedDriver: {firstName, lastName, profileImage?, rating} | null`, `null` until a driver is assigned. Deliberately did **not** widen the `.../location` carve-out's status check or touch `GET /drivers/:id` at all — the existing `assertJobAccess` check already run inside `JobService.getById` (customer/assigned-driver/owning-OWNER only) is sufficient to gate this; no new RBAC code was needed. Still no phone/email — call/message-driver affordances remain correctly omitted. Still no vehicle plate on this response (design step C-05 also wanted `DXB-42718`) — out of scope for this fix, `job.vehicleId` was already available separately if that's wanted later. No DB migration — `User.profileImage` was confirmed genuinely dead (never written anywhere in the backend, same category of finding as `Customer.averageRating` above); the photo actually comes from `Driver.profileImage`, the field `PATCH /drivers/:id` really writes to. `Driver.rating` was confirmed live (recomputed by `rating.service.ts` on every new rating). Backend: `driver.repository.ts`'s `findByIdWithPublicIdentity` (a real, explicit Mongo field-projection whitelist — no email/phone/companyId/documents/location ever leaves the database for this path), `job.service.ts`'s `getById`. Mobile: `types/entities.ts`'s `Job.assignedDriver`, `CustomerJobDetailScreen.tsx` (name + `Avatar` + rating, reusing the existing shared `Avatar` component). Tests: a new integration test in `job.test.ts` explicitly confirming another customer still gets 403 and the response never contains email/phone; 2 new component tests in `CustomerJobDetailScreen.test.tsx`.

### 14. Job creation required a `companyId` no Customer could legitimately obtain — RESOLVED 2026-08-10
- **Original finding**: `POST /jobs`'s schema required `companyId` as a mandatory 24-hex-char ObjectId, and there was no way for a Customer to obtain one — no company-listing endpoint exists (`CompanyRepository` has no `findAll`), and the one public lookup (`GET /companies/lookup/:companyCode`) deliberately never returns `_id`. The design shows zero company concept anywhere in the Customer flow. Full root-cause and architecture analysis (why `companyId` exists, who should select a company, comparison of 4 candidate architectures) is preserved below this entry for the historical record.
- **Resolution**: `POST /jobs` no longer accepts `companyId`/`companyCode` from the Customer at all — the request body is exactly `{serviceType, pickupLocation, destinationLocation}`. The backend resolves the platform's single operational company itself, server-side, via a new `DEFAULT_COMPANY_CODE` environment variable, looked up through the already-existing `CompanyRepository.findByCompanyCode()` (the same method `POST /drivers` already used for the identical "which company" problem — no new repository method, no `Company` schema change). Implemented in `job.service.ts`'s `resolveOperationalCompany()`, called from `JobService.create()` in place of the old `CompanyRepository.findById(input.companyId)`. If a client still sends a `companyId` field, Zod's default unknown-key-stripping silently discards it before it ever reaches the service layer — verified with a dedicated test (`jobDefaultCompany.test.ts`).
- **Error handling**: missing/misconfigured `DEFAULT_COMPANY_CODE` (unset, or set to a `companyCode` that doesn't resolve) returns `500` with a customer-safe message ("Booking is temporarily unavailable...") — never a 400/404 implying the customer did something wrong, and never names the env var. The server also logs a non-blocking startup warning if it's unset (`server.ts`), without hard-failing boot the way truly static secrets (`MONGO_URI` etc.) do — deliberate, since this value is intentionally re-resolved per-request rather than frozen at boot (see the code comment on `resolveOperationalCompany` for why: the integration test suite creates a fresh company per test run and only learns its `companyCode` after the app is already running).
- **Everything downstream is unchanged**: nearby-driver dispatch (`findNearbyAvailable`), the `company:<id>:fleet` socket room, `job.companyId` storage, and the full job lifecycle all continue to work exactly as before — only where the `company` variable comes from changed, not its shape or how it's used. Verified explicitly: a driver belonging to a *different* company, physically just as near, is still never offered the job.
- **Frontend**: `FareEstimateScreen`'s booking action, previously implemented but intentionally disabled, is now fully live — `createJob({serviceType, pickupLocation, destinationLocation})`, no `companyId` field anywhere in the mobile codebase. Customer booking (Home → Service Selection → Fare Estimate → Create Job → Finding Driver → Active Tracking → Completion → Rating) is now exercisable end-to-end, contingent on `DEFAULT_COMPANY_CODE` being set to a real company in the target environment (see the operational note below).
- **Deliberate scope limit — not a stand-in for real multi-company support**: this is a pragmatic single-operational-company simplification, chosen because (1) the design shows no company concept to the Customer at all, (2) the codebase's two closest sibling systems (Pricing config, Service catalog) already made the identical "global, not per-company" choice, and (3) `Company` has no geographic data today (no lat/lng, no coverage polygon — only unused `serviceAreas: string[]` text), so real geo-based multi-company matching isn't buildable without separate, net-new modeling work. **A future multi-company platform requires server-side company matching/routing based on real company coverage/geographic data** — not implemented here, and this fix should not be read as having solved multi-company dispatch.
- **Operational note**: at the time of this fix, this environment's database had zero `Company` documents (verified by direct query) — `DEFAULT_COMPANY_CODE` was added to `.env`/`.env.example` but left **blank**, not fabricated. An OWNER must create a real company via `POST /companies` and the env var must be set to its real `companyCode` before Customer job creation will succeed in this environment; until then, it correctly 500s with the configuration-error message described above rather than pretending to work.

### 15. `GET /jobs`, `GET /drivers`, `GET /notifications` returned zero results whenever their optional filter was omitted — RESOLVED 2026-08-10
- **Original finding**: discovered during Gap #14's operational (real-server) verification, not by any existing automated test — every one of these three list endpoints' repository methods built their Mongo query as `{ ...requiredScope, ...optionalFilter }` (e.g. `{ companyId, isDeleted: false, ...filter }`). When the optional filter (`status`/`approvalStatus`/`isRead`) was omitted by the caller, `filter`'s value for that key is `undefined`, not absent — and spreading `{ someKey: undefined }` into a Mongo query object keeps that key with an explicit `undefined` value. MongoDB matches an explicit `undefined` filter value against the deprecated BSON "Undefined" type, which no real document ever has — so the query silently matched nothing, every time, for every role, platform-wide. No existing test in the whole suite ever called any of these three endpoints without an explicit filter query param, which is exactly why this escaped detection until a real, unmocked end-to-end run surfaced it.
- **Real shipped mobile screens affected** (all call `listJobs`/`listNotifications` with no filter): Customer Trips (`CustomerJobsScreen`), both roles' Home-screen active-job lookup (`useMyActiveJob`, customer and driver), Driver's assigned-vehicle lookup (`useMyAssignedVehicle`), Driver Jobs (`DriverJobsScreen`), Owner's recent-jobs dashboard widget and "All" tab of `JobsListScreen` (which explicitly sends `status: undefined` for that tab — axios drops `undefined` params from the URL, so it hit the identical bug), and the shared `NotificationsScreen` (bell icon, all roles). Each of these would have rendered empty against a real backend, despite working fine in Jest (which mocks the API layer and never exercises this Mongo behavior).
- **Resolution**: added `omitUndefined()` (`src/utils/object.ts`, backend) — strips undefined-valued keys from an object before it's spread into a query. Applied at the exact 5 call sites: `job.repository.ts`'s `findManyByCompany`/`findManyByCustomer`/`findManyByDriver`, `driver.repository.ts`'s `findManyByCompany`, `notification.repository.ts`'s `findManyByReceiver`. No controller, service, route, request/response contract, pagination shape, or role-based access control changed — the fix is entirely inside how each repository assembles its Mongo query. Confirmed via full-backend search that these were the only 5 occurrences of this pattern.
- **No mobile code changes** — the mobile calls were already correct (omitting a filter is the right way to ask for "everything I'm allowed to see"); only the backend behavior was wrong.
- **Tests added**: `tests/integration/listFilters.test.ts` (backend) — for each of the three endpoints: no-filter returns everything the role can see, an explicit filter still narrows correctly, cross-company/cross-user data never leaks into an unfiltered list, and existing RBAC (e.g. only OWNER may call `GET /drivers`) is unchanged.

### 16. Push notification delivery (FCM) was previously listed above as "confirmed working end-to-end" — that was incorrect. RESOLVED at the source/build level 2026-08-12, not yet physically device-verified

- **Original finding**: a full QA audit (this session) plus an independent background-agent cross-check of every mobile API call against its backend contract both found the same thing: `notification.service.ts`/`firebase.provider.ts`/`deviceToken.*` are fully built and credentialed on the backend, but the mobile app never integrated a Firebase/push SDK and never called `POST /device-tokens` — so `DeviceTokenRepository.findByUserId` always returned an empty list for every real user, and `pushProvider.sendToTokens` was never actually invoked. Notifications only ever reached the app via the `notification:new` Socket.IO event, which requires the app to be open with a live connection — nothing arrived in a backgrounded or killed app, contradicting this doc's prior claim.
- **Fix**: `@react-native-firebase/app` + `@react-native-firebase/messaging` added; device-token registration wired into `AuthContext.tsx` at the same lifecycle point `SocketService.connect()` already uses; Android Gradle/manifest updated (Google Services plugin applied conditionally on `google-services.json` existing, so a missing file can never break the build); foreground notification UX deliberately untouched (Socket.IO remains the only thing driving it — FCM's `onMessage` is a no-op, purely to avoid duplicate popups). Full details: `PROGRESS.md`, "QA audit finding #1" entry.
- **Verified**: `tsc`/`eslint`/`jest` clean on both mobile and backend (no regressions, 46/46 mobile suites and 20/20 backend files passing), `gradlew assembleDebug` and `assembleRelease` both succeed and the Google Services plugin is confirmed to have actually parsed the real config (not just present-but-inert).
- **NOT yet verified**: actual token retrieval, actual registration reaching the backend, and actual push delivery to a backgrounded/killed real device — no physical device or emulator is available in this dev environment. Verify by installing the rebuilt APK on a real phone before claiming this end-to-end.
- **Known limitation, explicitly not fixed here**: the backend's FCM send has no `data` payload (`{title, body}` only), so a delivered push has no notification/job ID attached — tapping it can open the app but not deep-link to a specific screen. Out of scope for this fix (would require changing backend behavior).

### 17. `useProfileStatus.ts` treated any network/API failure identically to "no profile exists yet" — RESOLVED 2026-08-12

- **Original finding**: a full QA audit (this session) found `useProfileStatus.ts` only ever branched on `query.data` truthiness, never on `query.isError`, to decide between `'ready'` and `'no-profile'`. `getMyCompany`/`getMyDriverProfile`/`getMyCustomerProfile` all correctly return `null` (a successful query, no error) only on a genuine 404, and rethrow (surfacing as `isError`) on everything else (offline, timeout, 5xx) — but since both cases leave `query.data` equally `undefined`, the hook couldn't tell them apart. A real, already-completed Owner/Driver/Customer profile would get misreported as `'no-profile'` on nothing more than a dropped connection, sending them back through the full registration/onboarding flow — the exact scenario that already happened once this session when the ngrok tunnel dropped mid-use.
- **Fix**: added an `{ kind: 'error'; retry: () => void }` state to `ProfileStatus`, checked immediately after `isLoading` and before `data`, in all three role branches. `OwnerNavigator.tsx`/`DriverNavigator.tsx`/`CustomerNavigator.tsx` each render the existing shared `ProfileIncompleteScreen` component for it (no new UI component — reused the same component `DriverNavigator` already used for `pending-approval`/`rejected`), with a Retry action wired to the query's own `refetch()`. No backend endpoint or field touched — purely how the mobile app interprets responses it already receives. Full details: `PROGRESS.md`, "QA audit finding #2" entry.
- **Verified**: `tsc --noEmit` clean · `eslint .` clean · `jest`: 47/47 suites, 180/180 tests passing (18 new, covering loading/no-profile/ready/network-failure/500-failure/retry-recovery for Owner, the same plus the Driver-only approval branches for Driver, the same for Customer, and 3 tests confirming each role's session never calls another role's profile endpoint). No existing test encoded the old bug (both prior navigator tests mock the hook wholesale rather than exercising its real logic).
- **Not touched**: any Owner/Driver/Customer business functionality beyond this shared branch, `ProfileIncompleteScreen` itself, issues #1 (already resolved), #3–#7.

### 18. Driver Vehicle screen and Dashboard misrepresented a legitimate vehicle-reassignment 403 as either a scary generic error or silent "no vehicle" — RESOLVED 2026-08-12

- **Original finding**: `useMyAssignedVehicle.ts` (job-history-derived "my vehicle" workaround, gap #12) collapsed every non-2xx response from `GET /vehicles/:id` into one flat `isError` boolean, discarding the actual HTTP status. `DriverVehicleScreen.tsx` showed the generic `ErrorState` ("Something went wrong") for a 403; `DriverDashboardScreen.tsx` never checked `isError` at all and silently rendered "No vehicle information available yet." for the identical condition. Traced directly against `vehicle.service.ts` before any code changed: the backend's `getById`/`assertVehicleAccess` is correct — 404 first if the vehicle genuinely doesn't exist, 403 only if it exists but the requesting driver is no longer its current `assignedDriver` (e.g. the Owner reassigned it via "Reassign Driver", exactly what happened to `test-driver@admill.dev` during this session's own manual testing). Backend authorization was proven correct, not assumed, and was **not modified**.
- **Fix**: `useMyAssignedVehicle.ts` now returns a discriminated union (`loading` / `no-vehicle` with a `no-job-history`-vs-`vehicle-not-found` reason / `unauthorized` / `error` with `retry` / `ready` with the vehicle), reusing the existing `isForbiddenError`/`isNotFoundError` helpers from `api/client.ts` rather than inventing new classification logic — same discriminated-union pattern as issue #2's `useProfileStatus` fix, for consistency. Both consuming screens updated to branch on it; Vehicle screen now shows "Not assigned to you" (not a scary error) for a real 403, Dashboard shows the matching inline message — the two screens are now consistent for the first time. Full details: `PROGRESS.md`, "QA audit finding #3" entry.
- **Verified**: `tsc --noEmit` clean · `eslint .` clean · `jest`: 48/48 suites, 192/192 tests passing (12 new: 7 hook-level covering all 5 states plus retry-recovery, 4 on the Vehicle screen, 1 on the Dashboard — each explicitly asserting the *other* states' text does NOT appear, so 403/404/500 can never again be silently conflated). No existing test encoded the old bug — neither prior test file mocked the hook directly, and neither had a case that reached the 403 path.

### 19. `useIncomingJobOffer.ts` could silently drop a genuine job offer that arrived at launch/login, before the driver's own ID was known — RESOLVED 2026-08-12

- **Original finding**: `SocketService.connect()` fires in `AuthContext.tsx` the instant auth succeeds, but `DriverOfferOverlay` (the only place this hook's `job:new-request` listener ever registered) used to mount only once `DriverNavigator`'s `useProfileStatus()` reached `'ready'` — meaning no listener existed at all for the entire span of the post-login driver-profile fetch. A real offer broadcast to the company fleet room during that window reached the client's socket but had nothing there to catch it. A second, narrower window existed even once the listener was registered: the hook's own driver-ID lookup is asynchronous, so `handleNewRequest` used to silently `return` (permanently losing the event, no trace) whenever `myDriverIdRef.current` was still `null`.
- **Investigated and confirmed NOT a backend defect** in the area this issue covers: `admill-backend/src/config/socket.ts` has no `connectionStateRecovery` configured, so the transport genuinely never replays anything sent while disconnected — this fix only recovers events that reached a *connected* socket with *no listener yet*, never pretending to recover ones that were never delivered at all.
- **A genuine, separate backend timing gap WAS found during this investigation and is NOT fixed** (out of scope for this issue): `admill-backend/src/socket/index.ts`'s `registerSocketHandlers` calls `joinCompanyFleetRoom(socket)` as fire-and-forget (`void`, unawaited) inside the `connection` handler — a real window exists where a socket has finished connecting but hasn't yet joined its `company:X:fleet` room when a `job:new-request` is broadcast, meaning that specific delivery is lost server-side and no client-side fix can recover it. Flagged for a future, separately-authorized fix.
- **Fix**: `DriverNavigator.tsx` now mounts `DriverOfferOverlay` unconditionally, outside every `profileStatus` branch, instead of only inside `'ready'` — closing almost the entire real window structurally. `useIncomingJobOffer.ts` now uses a real `useQuery(['drivers','me'], getMyDriverProfile)` (the same cache entry `useProfileStatus` already uses, reactive rather than a one-off imperative fetch), buffers an offer that arrives before the ID is known (capped, re-evaluated the moment the query resolves) instead of dropping it, and permanently dedupes by job `_id` per hook-instance-lifetime so a duplicate/retried event can never reopen an already-resolved offer. Full details: `PROGRESS.md`, "QA audit finding #4" entry.
- **Verified**: `tsc --noEmit` clean · `eslint .` clean · `jest`: 49/49 suites, 199/199 tests passing (7 new: 4 hook-level covering the exact required scenarios — before-ID-resolves buffering, non-matching buffered offer suppressed, duplicate delivery not reopened, clean state on fresh mount with per-session dedup — plus 3 confirming the overlay mounts and can show a real offer during non-`'ready'` profile states). A real testing-library/React-Query test-infrastructure issue (not a source bug — confirmed via direct instrumentation) was found and fixed along the way: this library's own `act()` is always secretly asynchronous internally, and every un-awaited `act()` call in the test file was corrupting React's global act-environment flag for whichever test ran next.
- **Not touched**: backend socket/connection handling (including the fleet-room-join gap above — flagged, not fixed), Owner or Customer functionality, `DriverLocationTrackingRunner`'s mount timing (separate GPS concern), issues #1–#3 (already resolved), #5–#7.

### 20. Owner and Driver dashboard pull-to-refresh spinners never animated, even though the refresh itself worked — RESOLVED 2026-08-12

- **Original finding**: both `DashboardScreen.tsx` and `DriverDashboardScreen.tsx` hardcoded `<RefreshControl refreshing={false} onRefresh={refetchAll} />` — the pull gesture genuinely triggered `refetchAll` and data did refresh, but the spinner was wired to a literal `false`, so it never visually animated, making the gesture look broken even though it wasn't. Owner's `useDashboardData.ts` never exposed any fetching/refetching state at all (only `isLoading`/`isError`), which is why the screen had nothing real to bind to in the first place.
- **Fix**: `useDashboardData.ts` now derives `isRefetching` (aggregate `isFetching` across all its queries, excluding the initial load) and exposes it; `DashboardScreen.tsx` binds `refreshing={isRefetching}`. `DriverDashboardScreen.tsx` reuses its own already-declared `driverQuery`'s state directly (`refreshing={driverQuery.isFetching && !driverQuery.isLoading}`) — no new hook needed there. Neither screen's actual refresh behavior (what gets refetched) changed. Full details: `PROGRESS.md`, "QA audit finding #5" entry.
- **Verified**: `tsc --noEmit` clean · `eslint .` clean · `jest`: 49/49 suites, 202/202 tests passing (3 new — hook-level proof that `isRefetching` is only ever true during a genuine second fetch, plus one end-to-end test per screen proving `onRefresh` still triggers a real refetch with genuinely new data, not just a mock-function call). A test-environment limitation was found and worked around, not a source bug: this project's test renderer can't reliably inspect a native `RefreshControl`'s `refreshing` prop value directly (its `TestInstance` model only represents host elements, and the Jest-preset mock for the underlying native component doesn't forward that prop) — the fix's correctness is instead verified via the TypeScript-checked JSX itself plus the hook-level state test.
